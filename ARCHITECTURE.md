# Architecture

This document explains how the Adams Realty site is put together and why. Read
it before changing listing data, search, accounts or permissions. The firm is in
Royston and serves Northeast Georgia; its listings come from Georgia MLS and cover all
of Georgia (see "Coverage and the firm's area").

```
Browser ──► Next.js (App Router, React Server Components)
              │  pages render on the server from Postgres; client components only where
              │  interaction needs them (map, filters, forms, gallery)
              ├─ proxy.ts ............ preview gate, listing rate limits, account-page cookie check, demo noindex
              ├─ server actions ...... mutations (save home, lead forms, dashboard edits)
              ├─ /api/auth/* ......... Better Auth (sessions, password reset, OAuth)
              ├─ /api/cron/sync ...... scheduled MLS sync (Vercel Cron, bearer secret) + 7 a.m. lead summary
              ├─ /api/cron/alerts .... saved-search and saved-home emails + 7 a.m. lead summary
              └─ /api/locations/* .... search autocomplete
                        │
                        ▼
                    Postgres (Drizzle ORM) ◄── MLS sync ◄── RESO Web API (Georgia MLS)
```

## Listing data

**Sources.** Every listing belongs to a `data_sources` row:

- `manual`: listings our agents enter in the dashboard (pocket listings, coming-soon, rentals). Editable here. Coming soon, withdrawn, expired and canceled ones stay off the public site.
- `reso_web_api`: an MLS feed. A **read-only mirror**, because the MLS is the system of record. Edit in the MLS and the change arrives on the next sync.

**Model.** Column names follow the RESO Data Dictionary loosely, normalized for
display and search:

- Status and property type are enums.
- Search filters are promoted to real columns: pool, waterfront, basement, and so on.
- Long-tail features live in `features` jsonb.
- Prices are whole dollars (monthly rent for rentals).
- `removed_at` soft-hides listings that leave the feed. Saved homes then show "no longer available".

**One write path.** MLS sync, the seed script and the dashboard editor all call
`upsertListing()` (`src/lib/listings/persist.ts`), or its batch form `upsertListings()`,
which is the one implementation. It upserts the rows (one multi-row statement per page),
rewrites media and open houses only when their lists changed, and derives history events
(listed, price change, status change, sold, relisted) by diffing against the previous row
(`diffEvents`, unit-tested). Slugs are address-based plus a stable hash, and are never changed
after creation, so shared links don't break.

**Sync** (`src/lib/mls/sync.ts`; control flow in `sync-engine.ts`, pure and unit-tested with a
fake feed; the Postgres side in `sync-store.ts`):

1. A run first marks this source's `running` runs with no heartbeat for 300 s (the cron's
   `maxDuration`) as failed: they were cut off. If another run is still alive (an advisory
   lock serializes the check), an incremental or full run does nothing and is recorded
   `skipped`; a purge waits for it, and if it still can't start it is recorded `failed` and
   the cron answers 500. The dashboard warns when no purge has succeeded for 36 hours.
2. **Incremental** (default): fetch records in (`ModificationTimestamp`, `ListingKey`) order,
   200 per page (Media and OpenHouse expanded), and map each (`reso/mapper.ts`, pure and
   unit-tested). Records the seller opted out of (`InternetEntireListingDisplayYN = false`)
   are taken down. Pages are fetched by **keyset** (each asks for the records after the last
   one received), never by following `@odata.nextLink`, which servers build from `$skip`: a
   record changing mid-run would shift the pages and hide another. A run that caught up
   leaves a cursor (the newest timestamp), and the next starts 30 minutes before it
   (`UPDATE_LOOKBACK_MS`), so a record the MLS published late is still picked up. A run that
   stopped partway also saves the last key (`data_sources.sync_cursor_key`), and the next
   continues exactly after it, however many records share one timestamp.
3. Each page is written in one transaction together with the advanced cursor, about ten
   statements per page. A record whose `ModificationTimestamp` matches the stored row is
   skipped (no writes at all), unless it was taken down or its agent link changed on our
   side. A `full` run rewrites every record (the first load, or repairing rows after a
   mapper fix).
4. **Time budget:** given a deadline (the cron passes `maxDuration − 45 s`), the run stops
   between pages when the next page could end past it, and ends `partial`. The cursor is
   saved, so the next run resumes there. The first statewide load (`--full`) runs from the
   CLI, which has no budget. The feed client bounds every wait (`reso/client.ts`): a 60 s
   request timeout, Retry-After capped at 30 s, 120 s per page with its retries, and nothing
   past the deadline plus 30 s. A hung feed fails the run cleanly (logged, cursor saved,
   caches refreshed for the pages written) instead of the function being killed mid-run.
5. **Purge** (`?purge=1` / `--purge`, daily, purge-only): fetch the feed's keys for what the
   site shows (live statuses plus sales closed in the last year) and soft-remove the
   listings in that same scope whose key is gone. The keys travel as one array parameter,
   anti-joined through `unnest`, so a statewide feed's 200k+ keys fit (one parameter per key
   overflows Postgres's 65,535). The keys are paged by keyset too (`ListingKey gt 'last'`), so
   a listing leaving the feed mid-download can't make the purge miss (and remove) another. A
   key list cut short by the budget, or an empty one, removes nothing. More than 5% to remove aborts the run (`PurgeCapError`, shown as a warning in
   the dashboard) unless `--allow-large-purge` / `&allowLargePurge=1`.
6. After a run that changed anything (even one that then failed): the `places` autocomplete
   view is rebuilt, and the cron route revalidates the `listings` cache tag. Every run is logged in `sync_runs` (mode,
   status, counts, heartbeat, cursor) and shown in _Dashboard → MLS feeds_.

`src/lib/mls/sync.db.test.ts` runs the sync end to end against Postgres in `npm test`
(skip-unchanged, agent relinks, restores, takedowns, full rewrites, cursor and resume, stale
and concurrent runs). `npm run perf:sync-bench` checks the numbers against `adams_perf` (about 220k listings): 300
changed records in about 0.8 s at 0.11 statements per listing, unchanged records cost no
writes, a 206k-key purge in 2–4 s.

Adding a non-RESO feed means implementing `ListingProvider` (`src/lib/mls/types.ts`).

**IDX compliance built in:**

- The listing brokerage and agent are shown on cards and property pages.
- The source's `disclaimer` appears on every page that shows listings.
- A "data updated" time is shown.
- Suppressed addresses are honored (`hide_address`).
- Off-market listings are hidden and marked `noindex`.

## Search

- **URL is the source of truth.** `parseSearchParams` turns the query string
  into `SearchCriteria` and drops invalid values rather than erroring.
  `serializeCriteria` is its inverse and omits defaults. Every search is
  therefore linkable, works with back/forward, and is stored verbatim as a saved
  search.
- **SQL** (`buildConditions` / `buildOrderBy`, unit-tested by rendering SQL):
  - **A town is that town (site review #5).** When `q` names a city some public listing is in (`resolveTown`, `src/lib/search/place.ts`, looked up once per page and per alert run), the location condition is that city alone (`LocationScope.town`): "Hartwell" no longer pulls in every "Lake Hartwell" home in Lavonia and Toccoa. A ZIP stays a ZIP and a lake guide's name or alias stays a lake search (`lakeGuide`). Everything else is matched as below.
  - **Location:** ZIP match, or full-text search on `location_vector` (address, city, ZIP, neighborhood, lake from RESO WaterBodyName, MLS number; never the description), plus prefix and trigram matching for half-typed names and addresses. A guide name or alias ("Lake Hartwell", "Lanier"), or a section town's city (`cities`), also matches the way its guide does (`areaCondition`, inside the guide's counties). Each branch, the guide-name one included, has an index per scope (live listings, sold homes), so the matches of other statuses are never read. Nothing indexes the status alone: Postgres would AND a 50k–160k-row status bitmap into every location search (4 ms of a 6 ms page), and `src/lib/search/indexes.test.ts` fails if such an index comes back. `search_vector` (descriptions included) stays for keyword search.
  - **Map area:** `longitude BETWEEN … AND latitude BETWEEN …`, backed by a partial (latitude, longitude) btree. No PostGIS needed.
  - **Order:** one partial btree per sort order and mode (for sale, `pending=1`, sold; rent is small enough for one), each matching `buildOrderBy` exactly, so a page reads straight off an index. `src/lib/search/indexes.test.ts` checks the migrations against `buildOrderBy`/`buildConditions`.
  - **Filters:** ordinary indexed columns. With no property type picked, commercial is left out (`defaultTypesCondition`, `property_type <> 'commercial'`); land and farms stay in (owner decision). The home page's counts, town chips and places index use the same set (`forSaleNow`), and `listings_buy_geo_idx` carries `property_type` so viewport and default counts stay index-only.
  - **Land sorts (site review #8):** "Acreage (most first)" (`lot_desc`) and "Price per acre" (`price_per_acre_asc`, price over lot size), each with a partial index per mode (`drizzle/0012`).
- **Map pins** are a separate lightweight query over all matches, capped at 750 (the first 750
  in the search's order). Walking the order index reads 750 ÷ (share of rows matching) rows;
  for a location search Postgres can't judge that share and walked 20k rows for sold homes in
  Savannah (70–130 ms). So a location search picks the way itself (`walkPins`, from Postgres's
  row estimates): walk when matches are common along the order, else collect every match
  through the location indexes and keep the first 750 (`locationPins`, 12–15 ms there).
  Either way a place with thousands of matches reads one heap row per match, about 1 µs each
  on a warm local cache: `perf:measure` holds location pins to 12 ms for sale and 20 ms for
  sold (a plain search's to 5 ms). The clustered map endpoint (hand-off WP3) is what takes
  large pin sets off the request path.
  MapLibre clusters them and draws collision-aware price pills with dots underneath.
  The map loads its self-hosted web worker from `/vendor/maplibre/<version>/`.
- **Headings and places (site review #5).** The results heading follows the search (`searchHeading`): "Homes for sale in Hartwell" (the town as the listings spell it), "Homes near Lake Hartwell", "Homes in this map area", and by type "Land for sale in Georgia". Autocomplete folds a lake's rows (one per town) into one "Lake Hartwell (lake area)" suggestion, offers a lake guide whenever a word of its names is typed, and lists towns whose homes have all sold (`shapeAreaSuggestions`, `src/lib/search/suggest.ts`).
- **Moving the map drops the town.** A buyer's pan or zoom searches every home in view (`bounds`, no `q`), and the town is kept as `from` for "Back to Royston" (UI state like `view`; see `docs/mobile-contracts.md`).
- **No results is never a dead end.** The page offers an email alert (the save-search dialog: "Email me when homes list here", "…when rentals list here"), "See all … in Georgia", 2–3 nearby towns with homes for the search (`nearbyTowns`: filters kept when a town matches them, else the mode alone), and, for a place, the other mode's listings there ("Homes for sale in Carnesville (4)" on an empty rentals search, `EmptyHelp.elsewhere`); "Clear filters" shows only when filters are on. Its words follow the mode (`noResultsCopy`) and state only what the search checked ("No rentals in Carnesville right now", never "Nothing is listed"). The map goes to the searched place's listings of any status (`placeBounds`), else the state.
- **Scaling path.** Postgres handles a statewide MLS comfortably: `npm run perf:seed` builds
  `adams_perf` (about 220k synthetic listings: 45k for sale, 5k rentals, 160k closed) and
  `npm run perf:measure` times every search against its targets (default /homes page 1 in
  about 0.1 ms, its count about 5 ms). The rest of the app depends only on `searchListings` and
  `searchMapPins`, so swapping in Typesense or OpenSearch later is contained.

## Coverage and the firm's area

Listings cover all of Georgia; statements about the firm stay true to Northeast Georgia.
`src/config/site.ts` keeps the two apart:

- **`site.coverage`** (name "Georgia", the state's bounds) is what the listings cover. Search
  titles and headings ("Homes for sale in Georgia"), the root title, SEO copy about listings
  and the search map's first view use it.
- **`site.market`** (region "Northeast Georgia", the seven counties, their bounds, the time
  zone) is the firm. About, sell, agents, contact, the area guides and every "our agents"
  sentence use it, never `coverage`.
- **The firm's area** is `isFirmArea` (`src/lib/areas/firm-area.ts`, SQL twin
  `firmAreaCondition`): the listing's county is one of `site.market.counties`, or the
  listing belongs to an area guide inside that guide's counties (Lake Lanier homes in
  Forsyth, Braselton in Barrow). County-scoped, never by name alone, and false without a
  county. `offersTours` adds the firm's own listings anywhere.
  - Listing pages outside it offer "Ask a question" only (no tour tab, no in-person option,
    the phone CTA says the same) and say Adams Realty works mainly in Northeast Georgia.
    `createInquiry` turns a tour request for such a home into a question (`withoutTour`),
    it goes to the office inbox, and the reply names the office, not a local agent.
  - The home page's "Handpicked by our agents" takes only the firm's listings and firm-area
    homes, and is hidden when fewer than 4 qualify (`FEATURED_MIN`).
- **Towns are data, never a list in code.** The home page's town chips (up to 12, one
  swipeable row on phones) and the footer's Places column (6) are `getTopCities`, the
  cities with the most homes for sale; "See all towns" opens `/places`, every city with
  homes for sale grouped by county (`getPlacesIndex`, shaped by `placesIndexView`), the
  firm's counties marked. The seed checks that each chip's search finds its homes.
- **Map default view:** the search's bounds, else its pins, else `site.coverage.bounds`,
  always as a fit (no fixed center or zoom). On phones the map starts hidden (0×0), so a fit
  asked for then waits until the map is first shown (`pendingFit` in `search-map.tsx`).
- **Saved searches from the regional era:** `drizzle/0009` pins every saved search with no
  location (or just "Georgia"/"GA") to `site.market.bounds`, so its alerts don't widen to the
  whole state. It runs once, at the deploy that ships it (HANDOFF.md section 6, cutover order).
- **Payment estimates** use `financeFor(county)` (`src/lib/mortgage.ts`): the statewide
  defaults plus `site.finance.regions` (coastal insurance for Chatham, Glynn, Camden,
  Liberty, Bryan and McIntosh; a higher property-tax fallback for the metro and city-county
  governments). The home page never mentions monthly costs (owner decision); listing pages
  keep their estimate.

## Land and farms

Land is about one listing in five here, and is compared by acreage and price per acre
(site review #8). `src/lib/listings/land.ts` is the one place that decides it:

- **Bare land** (`isBareLand`) is a land or farm listing with no living area and no
  bedrooms. Cards, the map preview, recent sales and alert emails describe it as
  "Land · 12.5 acres · $8,400/acre" (`landSummary`), never "— bd · — ba".
- **Its page** says "About this property" (commercial and other property too), shows
  Acreage and Price per acre, and hides Year built, Garage, Price per sq ft, beds and
  baths; the phone bar reads "Land · X acres".
- **Its estimate** has no home insurance (there's no house) and no mortgage
  insurance, and says "Land loan: terms vary; check with your lender" next to the
  figure and in the calculator (`LAND_LOAN_NOTE`). The figure at the top of the page and
  the calculator's starting total are one function (`listingMonthlyCost`), and the land
  e2e test checks the amount. Farms with a house keep the home estimate. The home page
  still never mentions monthly costs.
- **Area guides** add "Median price per acre" (bare land and farms for sale with a lot
  size) when there is any.
- **The dashboard's lot size** is typed in acres by default, with a switch to square
  feet that converts the number; the database keeps square feet (`lotSizeToSqft`).

## Georgia MLS display rules

The IDX/Vendor Data License Agreement (Aug 1 2023; summary in `docs/plans/gamls-compliance.md`)
governs every listing that came from the feed. Adams Realty, Inc. is the licensee.

- **Which rows:** `listings.from_feed` (set by `upsertListings` from the source's kind) marks
  feed data, which the photo, removal and attribution rules below apply to. The hidden-status
  rule applies to every row: the firm hides its own manually entered listings in those statuses
  too (owner's decision, `drizzle/0011`).
- **Hidden statuses (Exhibit A §17):** the generated column `idx_hidden` is true for every row
  that is Coming Soon, Withdrawn (On Hold maps here; the status enum has no on-hold value),
  Expired or Canceled (`HIDDEN_STATUSES`, `src/lib/listings/hidden-statuses.ts`). Every public
  query starts from `publicListing()` / `publicConditions()` (`src/lib/listings/visibility.ts`):
  search and pins, cards, the sitemap, autocomplete (the `places` view), town chips, the
  places index, home stats, area guides, agent pages and alerts. `getListingBySlug` returns
  null for such a row, and for a feed row that left the feed (`removed_at`), so the page 404s.
  A saved home in that state shows "No longer available" with its address and firm only; it
  can be unsaved but not saved, and takes no inquiries. The dashboard still lists the firm's
  hidden listings with their exact status (`staffStatusLabel`), marked "Not public" in place of
  a link to the page, and the listing form says when a status keeps a listing off the site.
  `public_since` stays null until a hidden row first turns visible, so alerts announce a
  Coming Soon listing, feed or manual, when it goes active.
- **Primary photo only (§16, Exhibit C):** sold and off-market feed rows show one photo on the
  page (gallery, lightbox, JSON-LD) and on cards (`allowedPhotos` in `withPhotos`). OG images
  and map popups only ever use the primary photo. The firm's own sold listings keep every photo.
- **Attribution (§7, §10):** every card, map popup, area-guide tile and listing page names the
  listing firm in `text-sm`, the size of the other listing text (`e2e/gamls.spec.ts` measures
  it against the median). `MlsAttribution` (`src/components/content/mls-attribution.tsx`)
  shows the Georgia MLS name and logo and "Listing information © <year> Georgia MLS" in the
  footer, on the search page and in each feed listing's information block. The logo is the
  official GAMLS IDX logo supplied by Georgia MLS (`site.mls.logo`,
  `public/brand/gamls_idx.png`, 300 × 118): one image for both themes, on a white chip in the
  dark one, 32 px tall at its own aspect ratio, with "Georgia MLS" as its alt text. Every feed
  card, area-guide tile and map popup also carries `MlsCredit`: the logo at 24 px and
  "© <year> Georgia MLS" in `text-xs` (below the median, so the firm line stays at or above it).
  The IDX disclaimer is `site.mls.disclaimer` (a PLACEHOLDER until Georgia MLS gives its exact
  wording), copied into `data_sources.disclaimer` and shown on `/homes`.
- **Fields (Exhibit C):** the listing page's "Listing information" block shows Listing office,
  Listing ID, Status, and when the feed sends them the attribution contact phone and email,
  Variable Compensation, and buyer-agency compensation always together with its comments.
  The RESO mapper reads none of `EXCLUDED_FIELDS` (listing agreement, contract, on-market and
  expiration dates, private and office remarks, showing contact and requirements); the list
  date comes from `OriginalEntryTimestamp`. Tests feed a record carrying all of them through
  the mapper and into the database and look for them.
- **Corrections (§6):** `/listing-corrections` publishes the phone and email
  (`site.mls.corrections`) and a form (inquiry `source = 'report'`, emailed to the corrections
  address, never to an agent). Every listing page links to it with `?listing=<slug>`.
- **Traffic (§9):** `CountView` counts one view per listing page load (not crawlers) in
  `listing_views` (listing × market day). Admins see and export it at `/dashboard/traffic`
  (CSV, optionally Georgia MLS listings only).
- **Unbiased sort (§12):** only the default "Recommended" order looks at `is_featured`; every
  other sort ranks by the chosen field and id (`query.test.ts`, `idx-rules.db.test.ts`).
- **Anti-scraping (§3):** `proxy.ts` guards `/homes`, `/homes/*` and `/api/locations/*`
  (sitemaps excepted) with `src/lib/listing-guard.ts` (policy in `src/lib/anti-scraping.ts`,
  unit-tested; counting in Postgres, `rate_limits`, `src/lib/rate-limit-db.ts`, so the
  limits hold across serverless instances):
  - Self-declared HTTP libraries get a 403. Link-preview robots (LinkedIn, whose user agent
    names Apache-HttpClient, Facebook/iMessage, X, Slack, WhatsApp, Telegram, Discord)
    may GET pages, in their own small per-IP bucket (`preview:*`: 30 a minute, 200 an hour,
    500 a day, a tenth of a day's pages, since the user agent alone makes one), but not the
    API.
  - Not limited: staff (agents and admins), the office's addresses (`OFFICE_IPS`, comma-
    separated, IPv4 and IPv6 CIDR allowed, empty by default), loopback outside production (`next dev`,
    e2e runs), and Google/Bing crawlers confirmed by reverse + forward DNS
    (`src/lib/crawler-verify.ts`, cached per IP a day; a crawler name alone proves nothing).
    The DNS must end in googlebot.com or google.com (Bing: search.msn.com), never
    googleusercontent.com: every Google Cloud VM resolves there and back, so renting one
    would pass.
  - Signed-in buyers count per account (`account:*`, well above the per-IP limits) and, all
    together, per IP in their own allowance the size of the anonymous one (`members:*`,
    `members-quick:*`, `members-api:*`), never against the anonymous one: an address whose
    anonymous visitors are paused doesn't pause them, and accounts made from one address
    (sign-up checks no email) add one allowance, not one each. The flip side: a very busy
    shared address (a library, public Wi-Fi, carrier NAT), or one account scraping from it,
    can use up the members' allowance and pause every buyer signed in there, for up to a
    day. Only the office's own addresses (`OFFICE_IPS`) are never limited. The 429 page says
    which allowance ran out (the account, or the connection everyone signed in on it shares).
    The proxy verifies the session (Better Auth's signed cookie cache, else the `sessions`
    table; `src/lib/auth/proxy-session.ts`); a cookie's presence proves nothing.
  - "Per IP" means per IPv4 address, or per IPv6 /64 (a /48 for the daily windows;
    `ipLimitSubject`): one home, phone or server gets a whole /64 and can send from any of its
    2^64 addresses, so counting single IPv6 addresses would give it a fresh allowance per
    address. The form limits (`src/lib/form-guard.ts`) count the same way.
  - Everyone else: per client IP (Vercel's `x-forwarded-for`), per minute, hour and day, in
    units (`page:*`: 120 pages a minute, 1,500 an hour, 5,000 a day): a full page load costs
    `PAGE_UNITS` (4); the site's own client refreshes (map moves, filters, link taps, server
    actions) and link prefetches, "quick" requests, cost 1. Next strips its flight headers
    (`rsc`, `next-router-prefetch`) and `_rsc` before the proxy runs, so a quick request is
    recognized by the router's `next-url` header, `next-action`, a non-GET method,
    `Sec-Fetch-Dest: empty` or a prefetch `Purpose`; all can be forged, and a forged one gets
    a full page. So quick requests also count against their own cap (`quick:*`: 600 a minute,
    2,000 an hour, 6,000 a day, room for a busy person's prefetches): forged headers can at
    most double an address's pages an hour or a day (unit-tested).
  - Over a limit: the branded 429 page (`src/lib/busy-page.ts`, self-contained HTML in the
    site's light and dark palettes and the visitor's theme choice), with `Retry-After`. A
    pause of up to two minutes says "One moment, please" with Try again, Back, "Sign in and
    keep browsing" and the office phone. A longer one (an hourly or daily window) says
    "Listings are paused for now" and when they open again, and leads with "Sign in to keep
    browsing" (or, for a signed-in buyer, just Back), since Try again would only bring the
    page back. The API and labelled prefetches get plain text. A client refresh that gets the
    page makes the router load the URL, which shows it too.
  - Requests without an IP aren't limited; a database error lets the request through. The
    alerts cron prunes old counters.

## Accounts and permissions

- **Better Auth** handles sessions (httpOnly cookies, 5-minute signed cookie cache), email/password with reset, and optional Google sign-in. `role` is an additional user field that cannot be set at sign-up (`input: false`).
- **Roles:**
  - `user` (home shopper)
  - `agent` (linked to an `agents` profile)
  - `admin` (broker/staff)
- **Policy:** `src/lib/auth/permissions.ts` is the single place authorization is decided. It is pure functions with a full unit-test suite. Key rules:
  - Agents edit only their **own manual** listings. Nobody edits MLS listings.
  - Agents see only leads assigned to them. Admins see and route everything.
  - Admins can't change their own role, so the last admin can't lock everyone out.
  - Featuring a listing on the homepage is admin-only.
- **Enforcement layers:**
  1. `proxy.ts` bounces signed-out visitors early. This is only an optimization.
  2. Pages call `requireActor` / `requirePermission`, which redirect to sign-in or render a 403 via `forbidden()`.
  3. Every server action re-checks with `authorize(can.…)`. Sensitive staff actions are written to `audit_logs`.

## Leads

Tour requests, questions, valuations and listing reports go through one server action
(`createInquiry`, which calls `submitInquiry` in `src/lib/leads/submit.ts`). It validates
with zod and routes to the listing agent, the chosen agent, or the brokerage inbox
(unassigned, for an admin to route). Homes outside the firm's area take questions only,
answered by the office (see "Coverage and the firm's area"). The lead is saved first; the
email notification is best-effort. Leads are never shared outside the company.

**Lead emails** (`src/lib/leads/notify.ts`, site review #3):

- A new lead goes to its agent (or `LEADS_INBOX`, or the corrections contact for a listing
  problem report). Every admin with `users.lead_copies` on (the default; owner decision:
  Andrea sees every lead) gets a copy, unless it already went to them; spam and reports get
  none. When an admin assigns or reassigns a lead (or clears one from Spam back to its
  agent), that agent is emailed, unless they assigned it to themselves.
- Every email's button opens the lead itself, `/dashboard/leads/<id>` (Call and Text are
  there); signed out, sign-in brings them back to it.
- Server actions send with `afterResponse` (`src/lib/leads/deliver.ts`), i.e. Next's
  `after()`: on Vercel the function stays alive (`waitUntil`) until every email is sent,
  and the visitor doesn't wait for the mail provider. Each send is separate, so one failure
  doesn't stop the others; failures are logged. Without `RESEND_API_KEY` emails are logged.

**Follow-up** (`src/lib/leads/attention.ts`, `working-hours.ts`, site review #9):

- Office time is Mon–Fri 9–5 America/New_York. A new lead is **waiting too long** after 2
  office hours (owner decision): `workingCutoff(now)` turns that into a plain
  `created_at <= cutoff`, so the database picks them.
- **Needs attention** (top of the dashboard overview, scoped like the leads: an agent's own,
  the whole office for admins): new leads waiting too long (red, "Waiting 4 days"), tours in
  the next 48 hours, and open leads whose **Follow up on** date (`inquiries.follow_up_on`, a
  market-calendar day; Tomorrow / In 3 days / Next week, counted on the server) is today or
  earlier. The leads list flags the same.
- **First contact** (`inquiries.first_contacted_at`) is stamped the first time a lead moves to
  contacted or qualified (a status change or a note with "Mark as contacted") and never
  moves. Admins see each agent's average reply time over the last 90 days, in office time
  (`getReplyTimes`). Leads handled before it was recorded have none and don't count. Status
  changes are audited (`inquiry.status`), as are follow-up dates (`inquiry.follow_up`).
- **Morning summary** (`src/lib/leads/digest.ts`): at 7 a.m. Eastern each agent with a login
  gets their own Needs attention lists and each admin the office's; nothing to report, no
  email; `users.lead_digest` turns it off (Dashboard → Email settings). It has no cron of
  its own: `/api/cron/sync` (every 15 minutes on Vercel Pro) and `/api/cron/alerts`
  (hourly) both call it, so it goes out by about 7:15 a.m. Eastern; before 7 a.m. local it
  does nothing, and a row in `lead_digests` (recipient, day) claims each summary, so a
  later run never sends twice. A failed send deletes the claim for the next run.

**Spam** (`src/lib/spam.ts`, `src/lib/form-guard.ts`), on every public form (tour/question,
contact, agent, listing report, valuation, sign-up, saved searches):

- A honeypot field (`website`) and a timer: `<Honeypot />` and `useFormTimer()`
  (`src/components/ui/spam-guard.tsx`) add them. When the form mounts, the page fetches
  `GET /api/form-token`: the server's time, signed with `BETTER_AUTH_SECRET`
  (`src/lib/form-token.ts`, good for a day; a page that comes back into view with a token
  over 12 hours old fetches a fresh one, since phones keep tabs for days). The form sends
  it back (`formToken`; sign-up in the `x-form-token` header) and the server measures the
  time on its own clock, so a client can't claim one. Too fast (`MIN_FILL_MS`: 3 s for
  messages, 2 s for sign-up and saved searches, the latter timed from when the search page
  opened) or no valid token (posted straight to the server, forged, edited or expired) is
  suspect. One token carries at most three leads (`FORM_TOKEN_MAX_LEADS`, counted in
  `rate_limits` by the token's nonce); later leads on it are flagged `reused-timer`, so a
  script can't fetch one token, wait once and send every lead with it. Tokens aren't tied
  to the sender's address on purpose: a phone moving from Wi-Fi to mobile data, carrier NAT
  and iCloud Private Relay all change it mid-form, and a real lead would land in spam.
- Per-IP and per-email submission limits (per account for saved searches) in the same
  Postgres limiter, an IPv6 sender counted by its /64 (its /48 for the daily windows) like
  the listing limiter; emails are hashed in the counter keys. Over a limit the sender is
  asked to wait (with the office phone) and nothing is stored.
- A content filter for SEO pitches ("Google's index", "search visibility", "SEO"…) with a
  link, or two such phrases, from anyone the office hasn't worked with (`isKnownCustomer`:
  an earlier lead from that email or signed-in account that staff moved to contacted,
  qualified or closed). Nothing the sender controls alone counts: not an account under the
  typed email (agents' emails are public), not being signed in (sign-up checks no email),
  not an earlier lead nobody has answered.
- A suspect lead is stored with status `spam`, its reasons in `metadata.spam`, unassigned
  (the agent it would have gone to in `metadata.routedAgentId`) and never emailed; the
  sender sees the usual thank-you. It sits in Dashboard → Leads → Spam (with a count),
  flagged "Flagged automatically" with its reasons; it's left out of the dashboard's counts.
  Setting it to any other status gives it back its agent (audited). A suspect sign-up or
  saved search is refused with a "try again" message instead (a person passes a moment
  later); sign-up's checks run in a Better Auth `before` hook
  (`src/lib/auth/sign-up-guard.ts`), so posts straight to `/api/auth/sign-up/email` get
  them too.

## Mobile & PWA

Phones get an app shell (tab bar, sheets, full-screen search), and the site is
becoming an installable PWA. The design is in `docs/mobile-spec/`. Only the
foundation exists so far: the CSS contracts, primitives and helpers below.
`docs/mobile-contracts.md` lists the detail (markers, layers, e2e selectors,
storage keys) and marks what is reserved for which work package.

- **Variants.** `globals.css` defines `phone` (portrait phones, plus short
  landscape touch screens) and `wide` (everything else). App-shell decisions
  use them; sizing keeps `sm`/`md`/`lg`; `pointer-coarse:` gives touch devices
  44px buttons and 16px form controls, so iOS never zooms on focus. JS uses
  `PHONE_QUERY` or `useIsPhone()`, and a unit test keeps that query in step
  with the CSS.
- **Safe areas.** The layout draws under notches (`viewportFit: "cover"`) and
  content opts back in through `--sai-*` and the `*-safe` utilities built on
  them. Everything reads the variables, so e2e fakes a notch with
  `simulateNotch()`.
- **Chrome.** The header and tab bar are always rendered, and CSS hides them
  when a page renders a marker (`data-own-chrome`), never by pathname. The
  component that supplies the replacement renders the marker, so a page can't
  lose navigation before its replacement exists, and a 404 keeps it. Page bars
  declare `data-bottom-bar` (and `data-state="hidden"` when out of the way),
  which yields `--bottom-chrome-h` (static page padding, so layout never
  shifts) and `--bottom-overlay-h` (what the bars cover right now). Non-modal
  overlays that float over the page sit above the latter; today that is only
  the toaster, and the contracts doc lists the exceptions.
- **Full-screen search** will set `data-search-fullscreen` on the focused
  search `<form>`, turning the form itself into a fixed panel rather than
  opening a new input, so the keyboard stays up. For that to work no ancestor
  may create a containing block or stacking context; the CSS neutralizes those
  properties, and new code keeps them off anyway.
- **Layers** follow one z-scale (a comment in `globals.css`): bottom bars below
  the header (50), toasts above both (70), dialogs in the top layer.
- **e2e invariants.** /homes has one `[aria-live=polite]` (the results count)
  and one Save search button; a page has at most one `ContactForm` (so one
  `#c-name`); a listing's first `main p.tabular` is its price; and on pages
  that show listings, `article` means a `ListingCard`, so other tiles such as
  the map's preview strip must not be `article`s.
- **The `view` param is shared.** The "View" amenity filter is `view=1`. The
  phone results sheet keeps its position in the same key (`view=map` or
  `view=list`) so Back and relaunch restore it. Until the sheet exists (WP3),
  the list/map toggle below lg writes it: map is `view=map`, list is no value.
  The values tell them apart and both can appear
  (`?view=1&view=list`): `parseSearchParams` turns the filter on if any value
  is `1`, and sheet code reads and writes only its own value through
  `parseViewParam` and `setViewParam`. The sheet position is UI state, kept out
  of `SearchCriteria` and saved searches.
- **Device storage** (`src/lib/local-store.ts`, keys in `STORE_KEYS` from the
  React-free `src/lib/store-keys.ts`) is a
  convenience, never a source of truth: every access is wrapped in try/catch, a
  failure reads as "no data", and `recent.ts` sanitizes what it reads back
  because users can edit it. Recent searches, the last search (also in the
  `ar_last_search` cookie, for relaunch), recently viewed homes and the
  appearance (`ar:theme`) live there. This tab's sessionStorage (prefixes in
  `SESSION_KEYS`) holds where each results list was and the list a detail page
  was opened from (see "Getting back" below).
- **Getting back.** Browsing is open a home, look, go back, open the next, so
  Back never loses the buyer's place:
  - The results list scrolls inside its own box, which the browser doesn't
    restore, so `usePlaceRestoration` (search-view.tsx, `src/lib/search/restore.ts`)
    saves the scroll position, the tapped card and list or map per search URL
    and puts them back on Back, on reload and via "Back to results", outlining
    the card for a moment (`data-returned`).
  - Filter, sort and map changes replace the history entry; a new place and a
    new page of results push. Dialogs with `closeOnBack` and the photo viewer
    (`useDialogHistory`) close on Back before the page is left.
  - `ReturnLink` (`src/components/layout/return-link.tsx`) is the way back from
    a detail page: "Back to results" on a listing, "All leads", "Back to
    listings". When the list opened it in this tab (a one-time mark in
    sessionStorage, then a stamp on the page's history entry), it calls
    router.back(); otherwise it links to the last list (the last search for
    listings), else the plain list. Dashboard list pages render `ReturnSource`.
  - Signing in from a heart returns to the same URL with `save=<id>`; the saved
    homes provider saves it (`ensureSaved`) and drops the parameter. Sign-in
    replaces its own history entry. The heart tap also leaves a one-time intent in
    the tab's sessionStorage (`src/lib/save-intent.ts`, an hour), and only a
    matching one saves: a `?save=` link someone else made saves nothing.
- **PWA.** There is no service worker yet. `src/lib/pwa/protocol.ts` is the
  contract the page and the worker will share: which pages may be cached, and
  which requests are never intercepted (anything but GET, so no server action;
  RSC requests; private paths such as `/dashboard`). Caches that hold one
  user's data are purged before sign-out (`prepareSignOut()`).
- **Pending removal.** `SaveIntercept` and `SavedHomesProvider.setLocal()` let
  unsaving be undone without a server round trip; /saved adopts them in WP1.
- **Primitives.** `Dialog` keeps the native `<dialog>` and becomes a sheet on
  phones, sitting above the keyboard through `--kb-inset`; with `closeOnBack`,
  Back closes it. `toast()` renders inside an open dialog, where it stays
  clickable. `/dev/primitives` exercises both (a 404 in production).
- **Themes.** Every page works in light and dark (see "Themes" below). New UI
  uses the theme tokens and the class rules the theme guard enforces, and each
  package's new pages join the dark axe matrix. The switch lives in the header
  (`wide:`) and the phone menu (`phone:`); `theme-color` belongs to the theme
  code, and other code changes it only through `setChromeColor`.
- **Ownership during the mobile build.** Shared files (layout, `globals.css`,
  the `ui/` primitives, the helpers above, `e2e/mobile/` helpers and this file)
  are listed in `docs/mobile-spec/foundation.md` and edited only by the lead; a
  package that needs a change there sends a patch and a reason instead.
  `docs/mobile-contracts.md` is this section's detail split out, so it is
  lead-owned too. The
  packages run one at a time on one checkout, not in the spec's worktrees.

## Themes

Dark mode (docs/plans/dark-mode-and-georgia.md, "DM") is complete: the
mechanism, the class renames, the switch, the maps and the test matrix. The
theme files (`globals.css`'s tokens, `src/lib/theme*.ts`, `src/lib/store-keys.ts`,
`src/components/theme/`, `map-style.ts`) are lead-owned like the rest of the
foundation; `docs/mobile-contracts.md` ("Themes") lists what each work package
must keep.

- **Three appearances.** Match my device (the default) is no `data-theme` on
  `<html>`; Light and Dark set `data-theme="light|dark"`. The choice is stored in
  `ar:theme`. The custom `dark` variant in `globals.css` matches a forced Dark, or
  a dark OS unless Light is forced. Both branches are screen-only, so printing is
  light in every theme.
- **Tokens, not classes.** The `:root` block redefines the palette under
  `@variant dark`. Dual-role greens are split through Tailwind's per-utility
  namespaces (`--text-color-*`, `--border-color-*`, `--outline-color-*`,
  `--ring-color-*`, `--text-decoration-color-*`, `--accent-color-*`), so
  `text-brand-700` lightens in dark while `bg-brand-700` stays a fill. Never
  define `--background-color-*`: gradient stops read it too. Fills that change
  in dark use semantic tokens instead (`primary`, `primary-hover`); `shade`
  (overlays on photos and maps, toasts) never changes; `on-ink` is the label
  colour on a solid `bg-ink`; `map` is the map placeholder. Every new token
  equals today's palette in light, so light mode is unchanged. Named shadows are
  inlined by Tailwind and stay the same in both themes.
- **No flash.** `THEME_SCRIPT` (`src/lib/theme-script.ts`, React-free because the
  server layout imports it) runs first in `<head>` through `InlineScript`: it sets
  `data-theme` and prepends `meta#theme-color-override` for a forced theme. The
  viewport's `themeColor` pair covers Match my device. `<ThemeSync>` re-applies the
  stored choice after hydration (React's dev remount clears the attribute), and
  follows other tabs and pages restored from the back/forward cache.
- **Class rules** (enforced by `src/lib/theme-guard.test.ts`):
  - Overlays on photos, maps and the lightbox use `shade` (`bg-shade/80`,
    `from-shade/80`), never `ink`, which turns light in dark mode. A faint hover
    tint such as `hover:bg-ink/5` follows the theme on purpose.
  - Labels on a solid `bg-ink` use `text-on-ink`, not `text-white`.
  - Chips and buttons that sit on photos use `bg-surface` (`/90`, `/95`), not
    `bg-white`. White in both themes only where the guard allows it: the switch
    knob, carousel dots and the inverse button (`bg-white text-shade`, for brand
    panels).
  - The primary fill is `bg-primary hover:bg-primary-hover` (no `bg-brand-*`
    state on a `bg-primary` element); brand-700/800 stay for the fixed brand
    panels, photo frames and gradients.
  - No hex colours in class names: add a token. Map pins, clusters and price
    pills are the same in both themes and live in `MAP_OVERLAY_COLORS`
    (`search-map.tsx`).
  - `fill-*` utilities have no per-utility namespace: an icon whose fill must
    match its text colour uses `fill-current`.
- **The switch.** `<AppearanceControl>` (`src/components/theme/`) is a native
  radio group in a fieldset ("Appearance"): `list` rows in the header's
  `<ThemeMenuButton>` (a Popover, shown with `wide:`), `segmented` Auto / Light /
  Dark in the phone menu (shown with `phone:`, so a phone in landscape gets the
  menu, not the button). Each radio is stretched over its option, which is the
  44px tap target on coarse pointers and carries the focus ring. Choosing calls
  `writeThemePref` then `applyTheme`, which also updates the forced theme-color.
  It announces nothing (no live region).
- **Maps.** `mapStyleUrl(theme)` (`src/components/search/map-style.ts`):
  `NEXT_PUBLIC_MAP_STYLE_URL` or OpenFreeMap positron for light;
  `NEXT_PUBLIC_MAP_STYLE_DARK_URL`, else the custom light URL, else OpenFreeMap
  dark for dark. Both maps read the theme synchronously when created
  (`readResolvedTheme`), so they never start on the wrong style. The search map
  swaps with `swapDrawnStyle` (`setStyle(url, { transformStyle: carryOverlays })`),
  which carries the listings source and overlay layers across; `installOverlays` runs on every
  `style.load` and adds only what is missing, and `handleMissingImages` (MapLibre's
  missing-image resolver) supplies the pill images, and a blank pixel for icons a
  base style names but lacks. Event handlers are registered once. The location map
  is recreated on a theme change. `window.__searchMap` exists in dev only, for e2e.
  Both maps take their theme from `useMapTheme()`, which is light while printing,
  and `markDrawnStyle` sets `data-map-style` on the container once a style is drawn.
  On a swap, MapLibre keeps drawing (and idling on) the old style until the new one
  arrives, so `swapDrawnStyle` only counts an `idle` after its `transformStyle` has
  run with the new style.
  Print CSS hides any map canvas not marked `light`, because a print can't wait for
  a map to restyle: a dark page prints the light map panel, then the light map.
- **Client helpers** (`src/lib/theme.ts`, client components only):
  `readThemePref`/`writeThemePref`, `readResolvedTheme`, `applyTheme`,
  `setChromeColor` (for WP2's hero) and `watchTheme`; hooks `useThemePref`,
  `useResolvedTheme`, `useClientTheme` (client-only widgets: never null) and
  `useMapTheme` (light while printing) in
  `src/components/theme/use-theme.ts`. Emails stay light by design.
- **Tests.** Unit: `src/lib/theme.test.ts` (preference parsing, storage,
  `applyTheme`, the head script run against fakes, and drift between the CSS,
  the script and the module boundaries) and `theme-guard.test.ts` (the class
  rules above). e2e: `e2e/theme-suite.ts` holds the shared helpers and the dark
  axe matrix; `e2e/theme.spec.ts` runs on desktop (no flash, zero JS, the
  switch, persistence, Match my device, cross-tab, print (a listing, map
  included), maps, keyboard) and
  `e2e/mobile/theme.spec.ts` on the phone projects, including
  iphone13-landscape and ipad-mini. The dark axe matrix requires 0 contrast
  violations on every page with its own design, on desktop, pixel7 and
  iphone13; a new page adds itself to `DARK_AXE_PAGES`.
  `e2e/theme-light-regression.spec.ts` compares light pages pixel for pixel
  with baselines taken before dark mode (Windows, 1440×900); a change meant to
  alter light mode updates them in the same commit.
