# Architecture

This document explains how the Adams Realty site is put together and why. Read
it before changing listing data, search, accounts or permissions. The firm is in
Royston and serves Northeast Georgia; its listings feed comes from Georgia MLS.

```
Browser ──► Next.js (App Router, React Server Components)
              │  pages render on the server from Postgres; client components only where
              │  interaction needs them (map, filters, forms, gallery)
              ├─ proxy.ts ............ fast cookie check for /dashboard, /saved, /account
              ├─ server actions ...... mutations (save home, lead forms, dashboard edits)
              ├─ /api/auth/* ......... Better Auth (sessions, password reset, OAuth)
              ├─ /api/cron/sync ...... scheduled MLS sync (Vercel Cron, bearer secret)
              └─ /api/locations/* .... search autocomplete
                        │
                        ▼
                    Postgres (Drizzle ORM) ◄── MLS sync ◄── RESO Web API (Georgia MLS)
```

## Listing data

**Sources.** Every listing belongs to a `data_sources` row:

- `manual`: listings our agents enter in the dashboard (pocket listings, coming-soon, rentals). Editable here.
- `reso_web_api`: an MLS feed. A **read-only mirror**, because the MLS is the system of record. Edit in the MLS and the change arrives on the next sync.

**Model.** Column names follow the RESO Data Dictionary loosely, normalized for
display and search:

- Status and property type are enums.
- Search filters are promoted to real columns: pool, waterfront, basement, and so on.
- Long-tail features live in `features` jsonb.
- Prices are whole dollars (monthly rent for rentals).
- `removed_at` soft-hides listings that leave the feed. Saved homes then show "no longer available".

**One write path.** MLS sync, the seed script and the dashboard editor all call
`upsertListing()` (`src/lib/listings/persist.ts`), or its batch form `upsertListings()`,
which is the one implementation. It upserts the rows (one multi-row statement per page),
rewrites media and open houses only when their lists changed, and derives history events
(listed, price change, status change, sold, relisted) by diffing against the previous row
(`diffEvents`, unit-tested). Slugs are address-based plus a stable hash, and are never changed
after creation, so shared links don't break.

**Sync** (`src/lib/mls/sync.ts`; control flow in `sync-engine.ts`, pure and unit-tested with a
fake feed; the Postgres side in `sync-store.ts`):

1. A run first marks this source's `running` runs with no heartbeat for 300 s (the cron's
   `maxDuration`) as failed: they were cut off. If another run is still alive, it does nothing.
2. **Incremental** (default): fetch records with `ModificationTimestamp ≥ cursor`, oldest first,
   200 per page (Media and OpenHouse expanded), and map each (`reso/mapper.ts`, pure and
   unit-tested). Records the seller opted out of (`InternetEntireListingDisplayYN = false`)
   are taken down.
3. Each page is written in one transaction together with the advanced cursor, about ten
   statements per page. A record whose `ModificationTimestamp` matches the stored row is
   skipped (no writes at all).
4. **Time budget:** given a deadline (the cron passes `maxDuration − 45 s`), the run stops
   between pages when the next page could end past it, and ends `partial`. The cursor is
   saved, so the next run resumes there. The first statewide load (`--full`) runs from the
   CLI, which has no budget.
5. **Purge** (`?purge=1` / `--purge`, daily, purge-only): fetch the feed's keys for what the
   site shows (live statuses plus sales closed in the last year) and soft-remove the
   listings in that same scope whose key is gone. The keys travel as one array parameter,
   anti-joined through `unnest`, so a statewide feed's 200k+ keys fit (one parameter per key
   overflows Postgres's 65,535). A key list cut short by the budget, or an empty one, removes
   nothing. More than 5% to remove aborts the run (`PurgeCapError`, shown as a warning in
   the dashboard) unless `--allow-large-purge` / `&allowLargePurge=1`.
6. After a run that changed anything: the `places` autocomplete view is rebuilt, and the cron
   route revalidates the `listings` cache tag. Every run is logged in `sync_runs` (mode,
   status, counts, heartbeat, cursor) and shown in _Dashboard → MLS feeds_.

`npm run perf:sync-bench` checks all of this against `adams_perf` (about 220k listings): 300
changed records in about 0.8 s at 0.11 statements per listing, unchanged records cost no
writes, a 206k-key purge in 2–4 s.

Adding a non-RESO feed means implementing `ListingProvider` (`src/lib/mls/types.ts`).

**IDX compliance built in:**

- The listing brokerage and agent are shown on cards and property pages.
- The source's `disclaimer` appears on every page that shows listings.
- A "data updated" time is shown.
- Suppressed addresses are honored (`hide_address`).
- Off-market listings are hidden and marked `noindex`.

## Search

- **URL is the source of truth.** `parseSearchParams` turns the query string
  into `SearchCriteria` and drops invalid values rather than erroring.
  `serializeCriteria` is its inverse and omits defaults. Every search is
  therefore linkable, works with back/forward, and is stored verbatim as a saved
  search.
- **SQL** (`buildConditions` / `buildOrderBy`, unit-tested by rendering SQL):
  - **Location:** ZIP match, or full-text search on `location_vector` (address, city, ZIP, neighborhood, lake from RESO WaterBodyName, MLS number; never the description), plus prefix and trigram matching for half-typed names and addresses. A guide name or alias ("Lake Hartwell", "Lanier") also matches the way its guide does (`areaCondition`, inside the guide's counties). `search_vector` (descriptions included) stays for keyword search.
  - **Map area:** `longitude BETWEEN … AND latitude BETWEEN …`, backed by a partial (latitude, longitude) btree. No PostGIS needed.
  - **Order:** one partial btree per sort order and mode (for sale, `pending=1`, rent, sold), each matching `buildOrderBy` exactly, so a page reads straight off an index. `src/lib/search/indexes.test.ts` checks the migrations against `buildOrderBy`/`buildConditions`.
  - **Filters:** ordinary indexed columns.
- **Map pins** are a separate lightweight query over all matches, capped at 750.
  MapLibre clusters them and draws collision-aware price pills with dots underneath.
  The map loads its self-hosted web worker from `/vendor/maplibre/<version>/`.
- **Scaling path.** Postgres handles a statewide MLS comfortably: `npm run perf:seed` builds
  `adams_perf` (about 220k synthetic listings: 45k for sale, 5k rentals, 160k closed) and
  `npm run perf:measure` times every search against its targets (default /homes page 1 in
  about 0.1 ms, its count about 5 ms). The rest of the app depends only on `searchListings` and
  `searchMapPins`, so swapping in Typesense or OpenSearch later is contained.

## Accounts and permissions

- **Better Auth** handles sessions (httpOnly cookies, 5-minute signed cookie cache), email/password with reset, and optional Google sign-in. `role` is an additional user field that cannot be set at sign-up (`input: false`).
- **Roles:**
  - `user` (home shopper)
  - `agent` (linked to an `agents` profile)
  - `admin` (broker/staff)
- **Policy:** `src/lib/auth/permissions.ts` is the single place authorization is decided. It is pure functions with a full unit-test suite. Key rules:
  - Agents edit only their **own manual** listings. Nobody edits MLS listings.
  - Agents see only leads assigned to them. Admins see and route everything.
  - Admins can't change their own role, so the last admin can't lock everyone out.
  - Featuring a listing on the homepage is admin-only.
- **Enforcement layers:**
  1. `proxy.ts` bounces signed-out visitors early. This is only an optimization.
  2. Pages call `requireActor` / `requirePermission`, which redirect to sign-in or render a 403 via `forbidden()`.
  3. Every server action re-checks with `authorize(can.…)`. Sensitive staff actions are written to `audit_logs`.

## Leads

Tour requests, questions and valuations go through one server action
(`createInquiry`). It validates with zod, has a honeypot field and a per-IP rate
limit, and routes to the listing agent, the chosen agent, or the brokerage inbox
(unassigned, for an admin to route). The lead is saved first; the email
notification is best-effort. Leads are never shared outside the company.

## Frontend

- Server Components by default. Client components only where there's interaction.
- Design tokens are defined in `globals.css` (`@theme`): warm neutrals, evergreen brand, brass accent. Type is Fraunces for display and Inter for UI.
- Photos use a small `<Photo>` component (plain `<img>`, srcset for CDNs that resize, lazy loading, graceful fallback) rather than the Next image optimizer, which would be costly for tens of thousands of MLS photos.
- **SEO:**
  - Metadata per page.
  - `RealEstateListing` JSON-LD on property pages.
  - Sitemaps: `sitemap.xml` (pages, agents), `areas/sitemap.xml`, and the listings in 12 fixed
    chunks of up to 10,000 URLs at `/homes/sitemap/<id>.xml` (120k capacity; Georgia MLS has
    about 53k live). The chunk count is a constant, so `robots.txt` lists every chunk and no
    build needs a database (`sitemap-build.test.ts` fails if a sitemap or robots imports it).
- **Caching:** listing-derived data that only changes with the listings (home page stats,
  popular towns and featured homes, area guide stats, and GA-A's top cities and places
  index) goes through `src/lib/listings/cached.ts`: `unstable_cache` with the `listings`
  tag and a 15-minute backstop (the project doesn't use Cache Components). The cron sync
  revalidates the tag; dashboard listing and open-house actions `updateTag` it. Skipped
  outside production, so `npm run db:reset` under a dev server shows the new data at once.
- **Autocomplete** reads area names and counts from the `places` materialized view
  (neighborhoods, cities, ZIPs of live listings), rebuilt `CONCURRENTLY` after every sync,
  seed and dashboard listing change.
  - Canonical URLs for searches.
  - `noindex` on map-bounded and paginated search variants.

## Mobile & PWA

Phones get an app shell (tab bar, sheets, full-screen search), and the site is
becoming an installable PWA. The design is in `docs/mobile-spec/`. Only the
foundation exists so far: the CSS contracts, primitives and helpers below.
`docs/mobile-contracts.md` lists the detail (markers, layers, e2e selectors,
storage keys) and marks what is reserved for which work package.

- **Variants.** `globals.css` defines `phone` (portrait phones, plus short
  landscape touch screens) and `wide` (everything else). App-shell decisions
  use them; sizing keeps `sm`/`md`/`lg`; `pointer-coarse:` gives touch devices
  44px buttons and 16px form controls, so iOS never zooms on focus. JS uses
  `PHONE_QUERY` or `useIsPhone()`, and a unit test keeps that query in step
  with the CSS.
- **Safe areas.** The layout draws under notches (`viewportFit: "cover"`) and
  content opts back in through `--sai-*` and the `*-safe` utilities built on
  them. Everything reads the variables, so e2e fakes a notch with
  `simulateNotch()`.
- **Chrome.** The header and tab bar are always rendered, and CSS hides them
  when a page renders a marker (`data-own-chrome`), never by pathname. The
  component that supplies the replacement renders the marker, so a page can't
  lose navigation before its replacement exists, and a 404 keeps it. Page bars
  declare `data-bottom-bar` (and `data-state="hidden"` when out of the way),
  which yields `--bottom-chrome-h` (static page padding, so layout never
  shifts) and `--bottom-overlay-h` (what the bars cover right now). Non-modal
  overlays that float over the page sit above the latter; today that is only
  the toaster, and the contracts doc lists the exceptions.
- **Full-screen search** will set `data-search-fullscreen` on the focused
  search `<form>`, turning the form itself into a fixed panel rather than
  opening a new input, so the keyboard stays up. For that to work no ancestor
  may create a containing block or stacking context; the CSS neutralizes those
  properties, and new code keeps them off anyway.
- **Layers** follow one z-scale (a comment in `globals.css`): bottom bars below
  the header (50), toasts above both (70), dialogs in the top layer.
- **e2e invariants.** /homes has one `[aria-live=polite]` (the results count)
  and one Save search button; a page has at most one `ContactForm` (so one
  `#c-name`); a listing's first `main p.tabular` is its price; and on pages
  that show listings, `article` means a `ListingCard`, so other tiles such as
  the map's preview strip must not be `article`s.
- **The `view` param is shared.** The "View" amenity filter is `view=1`. The
  phone results sheet (WP3; nothing writes its position yet) will keep its
  position in the same key (`view=map` or `view=list`) so Back and relaunch
  restore it. The values tell them apart and both can appear
  (`?view=1&view=list`): `parseSearchParams` turns the filter on if any value
  is `1`, and sheet code reads and writes only its own value through
  `parseViewParam` and `setViewParam`. The sheet position is UI state, kept out
  of `SearchCriteria` and saved searches.
- **Device storage** (`src/lib/local-store.ts`, keys in `STORE_KEYS`) is a
  convenience, never a source of truth: every access is wrapped in try/catch, a
  failure reads as "no data", and `recent.ts` sanitizes what it reads back
  because users can edit it. Recent searches, the last search (also in the
  `ar_last_search` cookie, for relaunch) and recently viewed homes live there.
- **PWA.** There is no service worker yet. `src/lib/pwa/protocol.ts` is the
  contract the page and the worker will share: which pages may be cached, and
  which requests are never intercepted (anything but GET, so no server action;
  RSC requests; private paths such as `/dashboard`). Caches that hold one
  user's data are purged before sign-out (`prepareSignOut()`).
- **Pending removal.** `SaveIntercept` and `SavedHomesProvider.setLocal()` let
  unsaving be undone without a server round trip; /saved adopts them in WP1.
- **Primitives.** `Dialog` keeps the native `<dialog>` and becomes a sheet on
  phones, sitting above the keyboard through `--kb-inset`; with `closeOnBack`,
  Back closes it. `toast()` renders inside an open dialog, where it stays
  clickable. `/dev/primitives` exercises both (a 404 in production).
- **Ownership during the mobile build.** Shared files (layout, `globals.css`,
  the `ui/` primitives, the helpers above, `e2e/mobile/` helpers and this file)
  are listed in `docs/mobile-spec/foundation.md` and edited only by the lead; a
  package that needs a change there sends a patch and a reason instead.
  `docs/mobile-contracts.md` is this section's detail split out, so it is
  lead-owned too. The
  packages run one at a time on one checkout, not in the spec's worktrees.

## Testing

- **Unit (Vitest):** permissions, RESO mapper, event diffing and slugs, search
  parsing and SQL, formatting, mortgage math, time zones, geocoder, rate
  limiter; for mobile, device storage and recents, the PWA protocol and purge,
  the dialog's keyboard and swipe math, the toast store, deep links and idle
  scheduling.
- **End-to-end (Playwright, `e2e/`):** public pages (desktop and mobile),
  accounts, saving, tour requests, dashboard permissions, admin listing
  creation. Runs against a seeded database.
- **Phones (`e2e/mobile/`):** the `pixel7` and `iphone13` projects run every
  spec there; `iphone13-landscape` and `ipad-mini` run `sweep` and
  `*landscape*` specs plus tests tagged `@landscape`. The `desktop` project
  skips the folder. `helpers.ts` has the touch gestures and the environment
  fakes (`simulateNotch`, `simulateKeyboard`); `axe-allowlist.ts` lists the
  known serious accessibility findings, each with an owner and a reason.
